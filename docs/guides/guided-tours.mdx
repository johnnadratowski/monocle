title: "Guided Tours"
description: "Let your agent walk you through a change, one stop at a time."

A review lands in whatever order its files sort. Your agent knows the order it should be read in and what to say at each point — a guided tour is how it tells you. The tour is an ordered list of **stops**, each a place in the diff plus the agent's note about it. You step through with a key and ask the agent about any stop by its id: "1.2 — does `x` get hoisted here?".

## Taking a tour

When the agent sends a tour, monocle enters **tour mode** on its first stop and **hides the file list**: the tour moves between files for you, so the list is the exception. `;` (`toggle_sidebar`) shows it again, and it stays as you leave it — a re-sent tour, `goto_stop` or `W` do not hide it again. A tour restored on launch hides it too. Each stop:

1. Selects the stop's file and puts the diff cursor on its first line. The stop's lines stay marked in the gutter after you move off them.
2. Opens the doc pane under the diff with the header `1.2 · Title` and the agent's note, followed by the stops its code calls, its related files and its views as labels — `[1] → 1.3 saveToken`, `[1] src/auth/idp.ts:12`, `[2] video Login flow`, underlined. Clicking a label does exactly what its command does: `:call 1`, `:related 1`, `:view 2`. The pane is as tall as its note, up to 40% of monocle's window. The labels stay pinned to its bottom, so a note too long for it never pushes them out of reach: only the note above them scrolls — with the mouse wheel over it, or `j`/`k` once `Tab` has moved focus to the pane — and its header says how much is out of sight (`↓ 12 lines`).
3. Shows `tour 1.2 · 3 of 7` (the stop id, then its position in the tour) in the status bar.

| Key | Action |
|-----|--------|
| `.` | Next stop |
| `,` | Previous stop |
| `backspace` | Back to the stop you came from — see [Calls](#calls). |
| `f19` | Forward again. |
| `W` | Tour mode on/off. Off hides the note, the marks and the status; your stop is kept, and `.`/`,` or `W` resume there. |
| `X` | Close the related-files pane. |
| `:stop <id>` | Jump to a stop by id, e.g. `:stop 1.2`. With no id it lists the stops. |
| `:view [n]` | Open the stop's nth view (default the first): through your on-stop command when you have one (see [below](#screenshots-recordings-and-layouts)), else in your [`media_viewer`](/configuration/config-file) — or `markdown_viewer` for a markdown view. |
| `:related [n]` | Bring up the stop's related files with the nth (default the first) active — see [Related files](#related-files). |
| `:call [n]` | Go to the stop the stop's nth call (default the first) leads to — see [Calls](#calls). |
| `:back` / `:forward` | The same as `backspace` / `f19`. |
| `:layout [reset]` | Say whether the tour's windows are in a saved layout; `reset` puts back the default — see [Which views are showing](#which-views-are-showing). |

The ends clamp: `.` on the last stop tells you it is the end rather than wrapping to the first. A stop with no file — one that exists to show a recording, say — shows its note and leaves the diff where it is. `ctrl+o` returns to wherever a stop jumped you from.

The tour belongs to the review. It survives a restart (you come back on the same stop), and it goes when the review is cleared or approved.

## Calls

A stop's code often calls the function a later stop is about: 2.1 is the withdrawal route, and it calls `requestWalletWithdrawal`, which is what 2.2 explains. The agent says so with the stop's `calls`, and each shows in a **Calls:** row, the first under the note: `[1] → 2.2 requestWalletWithdrawal`, `[2] 4.1 dispatchHold`. The call that leads to the **next** stop reads `→` and is coloured apart from the rest. Clicking one, or `:call N`, enters that stop as `:stop` would.

Following a call is a detour, so the tour keeps a **history** of the stops you enter — by `.`/`,`, `:stop`, a call, or the agent moving you — and walks it the way a browser walks pages. `backspace` (or `f18`) goes back to the stop you came from, `f19` goes forward again, and entering another stop after going back drops the stops forward would have reached. The status bar says where you went: `back to 2.1`, or `no earlier stop`. These keys work in tour mode only, and never while you are typing a comment, a search or a command. The history lasts as long as monocle runs.

## Related files

A stop can name **related files** — typically where a change starts, when the stop shows where it lands. When you settle on such a stop, monocle opens them together in **one tmux pane** beside it, running your editor ([`editor`](/configuration/config-file), else `$VISUAL`/`$EDITOR`):

- **vim / nvim** open every file **read-only** as a horizontal split (`nvim -R -o a b`), each window at its line. Read-only because the pane usually sits in the worktree under review, where one stray keypress would edit the change.
- Other editors open the first file, at its line.

The next stop with related files **reuses** that pane (`tmux respawn-pane`) instead of splitting another; a stop without any leaves it as it is. `X` closes it. The pane is split beside monocle's own (stacked instead with `editor_mode: "tmux_horizontal"`), and it does not take focus unless you set `editor_focus: true` — the tour is driven from monocle, and a split that took the keyboard would swallow your next `.`. Related files need monocle to be running inside tmux.

To get one back — after `X`, say, or to look at the second file — click its label or type `:related N`. That brings the pane up with **all** of the stop's related files, as arriving does, with file N's window the active one (vim/nvim end on `Nwincmd w`; other editors open file N): it respawns the pane when it is open and splits it when it is not. If monocle's tmux window is zoomed — a "hide everything" key that zooms monocle's pane, say — it is unzoomed so the pane can be seen, and the `@stage_zoomed` window option such a key sets is cleared. Keyboard focus follows the same rule as on arriving.

Side effects wait until you rest on a stop for a moment, so holding `.` to skip ahead does not open a pane per stop.

## Screenshots, recordings and layouts

A stop can carry **views** — screenshots, screen recordings, rendered documents, pages, artifacts — and a **layout** name. monocle does not open windows itself on a stop. It hands the stop to one command you configure, [`walkthrough_on_stop`](/configuration/config-file), which it runs on every stop you settle on:

```json
{ "walkthrough_on_stop": "stage on-stop" }
```

The command runs with `sh -c` in the repo root, in the background and with a 30-second timeout, so it never blocks the TUI; a failure shows in the status bar with the last line it wrote to stderr. It gets the stop in its environment:

| Variable | Value |
|----------|-------|
| `MONOCLE_STOP_ID` | The stop's id, e.g. `1.2` |
| `MONOCLE_REPO_ROOT` | The repository root |
| `MONOCLE_STOP_JSON` | The whole stop as JSON — `id`, `title`, `file`, `line_start`, `line_end`, `note`, `related`, `views`, `calls`, `layout` — with each view's `target` resolved: repo-relative paths made absolute, artifact ids made into the file holding the artifact |

What the command does with it is up to you: open the recording in a browser, arrange windows into the stop's layout, anything.

`:view N` asks the same command for one view, with the same environment plus two variables. The command opened the stop's views, so it is the one that can bring back the window already showing a view instead of opening a second:

| Variable | Value |
|----------|-------|
| `MONOCLE_VIEW_INDEX` | Which view, 1-based: its position in the stop's `views` |
| `MONOCLE_VIEW_NAME` | The view's name: `view` for the first, then `view2`, `view3`… |

When these are set, show that one view — open it, or raise it if it is already open — and leave the rest of the screen as it is: the reviewer asked for a view, not for the stop again. Without an on-stop command, `:view N` opens the view in your `media_viewer` (or `markdown_viewer`).

### Which views are showing

The windows your on-stop command opens are out of monocle's sight, so it cannot tell on its own whether a view is showing. Configure [`walkthrough_view_status`](/configuration/config-file) and it will ask, then mark each view's label: `[1] video Login flow (open)`, `(hidden)` or `(not opened)`.

```json
{ "walkthrough_view_status": "stage view-status" }
```

The command runs like the on-stop command — `sh -c` in the repo root, with `MONOCLE_STOP_ID`, `MONOCLE_REPO_ROOT` and `MONOCLE_STOP_JSON` — but has only 500 ms, since it is asked often and a slow answer must never be felt. It prints one line of JSON to stdout:

```json
{ "views": { "view": "open", "view2": "hidden" }, "layout": "default" }
```

`views` is keyed by view name — `view` for the first, then `view2`, `view3`…:

| Value | Marker |
|-------|--------|
| `"open"` | `(open)` — on screen |
| `"hidden"` | `(hidden)` — open, but out of sight |
| `"closed"`, anything else, or no key for the view | `(not opened)` |

`layout` is `"saved"` when the windows are in a layout you arranged, `"default"` otherwise. The note always shows it flush right on the view's row: **`layout default`**, or **`layout saved · reset`**. Clicking `reset` — or typing `:layout reset` — runs [`walkthrough_layout_reset`](/configuration/config-file) (`sh -c` in the repo root, with the same environment as the status command, 10-second timeout) and then asks the status again, so the label goes once the layout is back to the default:

```json
{ "walkthrough_layout_reset": "stage layout-reset" }
```

Answer for the stop in the environment: a window still showing another stop's view is not this stop's view. Without the command, or when it fails, times out, or prints anything without a `views` object, nothing shows — no markers, no layout label — since monocle does not know, so it does not say.

It is asked when a stop is shown (once the on-stop command has finished with it, when there is one, so the markers describe this stop's windows rather than the last stop's) and after `:view N` or a click. Only the latest answer for the stop you are on is used.

## Asking about a stop

Stop ids are what you type and what the agent answers to. When you ask about one, the agent can call `goto_stop` to put that stop in front of you while it explains.

A comment you write while the tour is on is tagged with the stop you were on: it shows `[1.2]` in its box, and the feedback the agent receives leads with it — `[1.2] Does x get hoisted here?` — so the agent reads it against what it said at that stop. If the agent re-sends the tour — to fix a note, say — you stay on the stop you were on as long as its id survives.

## Sending a tour

Agents send tours with the `set_walkthrough` MCP tool or `monocle review set-walkthrough --file tour.json`. See [Agent commands](/reference/agent-commands#monocle-review-set-walkthrough) for the format.
