---
title: "Guided Tours"
description: "Let your agent walk you through a change, one stop at a time."
---

A review lands in whatever order its files sort. Your agent knows the order it should be read in and what to say at each point — a guided tour is how it tells you. The tour is an ordered list of **stops**, each a place in the diff plus the agent's note about it. You step through with a key and ask the agent about any stop by its id: "1.2 — does `x` get hoisted here?".

## Taking a tour

When the agent sends a tour, monocle enters **tour mode** on its first stop and **hides the file list**: the tour moves between files for you, so the list is the exception. `;` (`toggle_sidebar`) shows it again, and it stays as you leave it — a re-sent tour, `goto_stop` or `W` do not hide it again. A tour restored on launch hides it too. Each stop:

1. Selects the stop's file and puts the diff cursor on its first line. Stop lines the compact diff hides between its hunks are revealed, with three lines either side; the rest of the file stays compact. The stop's lines stay marked in the gutter after you move off them, in magenta. The stops around it are marked too, so you can see where the tour goes from here: the previous stop in blue, the next in green, the one after it in bright green.
2. Opens the doc pane **above** the diff — the note is read before the code it is about — with the header `1.2 · Title` in the tour's cyan, then, dim, where the stop is — `src/auth/login.ts:40–52`, or `:40` for one line — and, under a rule, the agent's note. The note is all the pane holds: the stop's views show in the windows around monocle (see [Screenshots, recordings and layouts](#screenshots-recordings-and-layouts)), and the stops its code calls are underlined in its code (see [Calls](#calls)). The pane is the same height on every stop, a third of monocle's window by default ([`tour_note_percent`](/configuration/config-file) sets another share), so the code under it does not jump from stop to stop. A note too long for it scrolls — with the mouse wheel over it, or `j`/`k` once `Tab` has moved focus to the pane — with a scrollbar down its right edge. Its header says how much is out of sight (`↓ 12 more lines`, `↑ 3 · ↓ 9 more lines`), and its last row says so where your reading stops: `↓ 12 more lines` on the left, `lines 1–8 of 20` on the right, and `end of note` once you are at the end. A note that fits has neither. In a narrow pane the location gives way before the title does: directories drop from its left (`…/auth/login.ts:40–52`), never its file name and lines.
3. Shows `tour 1.2 · 3 of 7` (the stop id, then its position in the tour) in the status bar, and names the tour in the middle of the top bar, where the review's name was: `Tour for PR #308: Signup fixes` for a tour titled `PR #308 · Signup fixes` (a title starting `PR #<n>`, then `·`, `:`, a dash or a space), `Tour: <title>` for any other. `W` gives the top bar back to the review's name.
4. Marks the note's title with whether you have been on this stop before: a bright **`new`** the first time, a dim **`✓`** after. It is decided as you arrive and stays for the whole visit, so it does not change while you read. Every way of reaching a stop counts — `.`/`,`, `:stop`, a call, back and forward, the agent's `goto_stop`. The visited stops are kept with the review, by tour title and stop id, so restarts keep them; a tour sent under another title starts afresh, and withdrawing the tour (`set-walkthrough --clear`) or ending the review forgets them.

| Key | Action |
|-----|--------|
| `.` | Next stop |
| `,` | Previous stop |
| `backspace` | Back to the stop you came from — see [Calls](#calls). |
| `f19` | Forward again. |
| `W` | Tour mode on/off. Off hides the note, the marks and the status; your stop is kept, and `.`/`,` or `W` resume there. |
| `d` | Hide the stop's note, and show it again. With the cursor on an annotation, `d` opens the annotation's doc links instead, as outside a tour. |
| `:stop <id>` | Jump to a stop by id, e.g. `:stop 1.2`. A chapter's number, `:stop 5`, goes to its first stop (an exact id wins); `:stop` alone goes to the tour's first stop. |
| `:view [n]` | Open the stop's nth view (default the first): through your on-stop command when you have one (see [below](#screenshots-recordings-and-layouts)), else in your [`media_viewer`](/configuration/config-file) — or `markdown_viewer` for a markdown view. |
| `:call [n]` | Go to the stop the stop's nth call (default the first) leads to — see [Calls](#calls). |
| `:back` / `:forward` | The same as `backspace` / `f19`. |
| `:doc on`, `:doc off`, `:doc toggle`, `:doc` | Hide or show the stop's note (`-` toggles), the diff taking its rows. A new stop's note comes up shown. |

The ends clamp: `.` on the last stop tells you it is the end rather than wrapping to the first. A stop with no file — one that exists to show a recording, say — shows its note and leaves the diff where it is. `ctrl+o` returns to wherever a stop jumped you from.

The tour belongs to the review. It survives a restart (you come back on the same stop), and it goes when the review is cleared or approved.

## Calls

A stop's code often calls the function a later stop is about: 2.1 is the order route, and it calls `createOrder`, which is what 2.2 explains. The agent says so with the stop's `calls`, each naming the `symbol` called and, optionally, the `line` of the call. monocle underlines each symbol in the stop's lines, faintly, in yellow — on its call's line only, when the call has one. `u` and `U` move the cursor between the underlined lines, and `o` on one enters the stop its call leads to, as `:stop` would; so does `:call N`, for the stop's Nth call.

Following a call is a detour, so the tour keeps a **history** of the stops you enter — by `.`/`,`, `:stop`, a call, or the agent moving you — and walks it the way a browser walks pages. `backspace` (or `f18`) goes back to the stop you came from, `f19` goes forward again, and entering another stop after going back drops the stops forward would have reached. The status bar says where you went: `back to 2.1`, or `no earlier stop`. These keys work in tour mode only, and never while you are typing a comment, a search or a command. The history lasts as long as monocle runs.

## The editor beside monocle

What you open from the code — what lines reference (`ctrl+]`, below), the file on the cursor's line in a tour (`ctrl+g`), a file the agent asks for (`open_editor`) — opens in **one tmux pane** beside monocle, running your editor ([`editor`](/configuration/config-file), else `$VISUAL`/`$EDITOR`):

- **vim / nvim** open every file **read-only** as a horizontal split (`nvim -R -o a b`), each window at its line. Read-only because the pane usually sits in the worktree under review, where one stray keypress would edit the change.
- Other editors open the first file, at its line.

The next file opened **reuses** that pane (`tmux respawn-pane`) instead of splitting another. Respawning brings back every file the pane was given, including ones you closed in the editor; with [`related_editor_add`](/configuration/config-file) set, a file opened while the pane is alive is added to the editor already there instead, so a file you closed stays closed. With [`related_open`](/configuration/config-file) set, no pane is split at all: each file goes to that command — a popout window, say.

The pane is split beside monocle's own (stacked instead with `editor_mode: "tmux_horizontal"`) and takes the keyboard, so you see where the file landed. If monocle's tmux window is zoomed, it is unzoomed so the pane can be seen, and the `@monocle_zoomed` window option is cleared. `ctrl+shift+g` still takes over the screen. The pane needs monocle to be running inside tmux.

Paths are opened in the review's own checkout — the one the engine serves — even when monocle was started somewhere else and pointed at that engine with `--socket`, such as from the main clone against a worktree's engine.

A stop's `related` files are no longer shown or opened: the windows around monocle show what a stop is about. A tour that still carries them loads, and your on-stop command still receives them.

Side effects wait until you rest on a stop for a moment, so holding `.` to skip ahead does not run the on-stop command per stop.

## Screenshots, recordings and layouts

A stop can carry **views** — screenshots, screen recordings, rendered documents, pages, artifacts — and a **layout** name. monocle does not open windows itself on a stop. It hands the stop to one command you configure, [`walkthrough_on_stop`](/configuration/config-file), which it runs on every stop you settle on:

```json
{ "walkthrough_on_stop": "tour-hook on-stop" }
```

The command runs with `sh -c` in the repo root, in the background and with a 30-second timeout, so it never blocks the TUI; a failure shows in the status bar with the last line it wrote to stderr. It gets the stop in its environment:

| Variable | Value |
|----------|-------|
| `MONOCLE_STOP_ID` | The stop's id, e.g. `1.2` |
| `MONOCLE_REPO_ROOT` | The repository root |
| `MONOCLE_STOP_JSON` | The whole stop as JSON — `id`, `title`, `file`, `line_start`, `line_end`, `note`, `related`, `views`, `calls`, `layout`, `order` — with each view's `target` resolved: repo-relative paths made absolute, artifact ids made into the file holding the artifact |

What the command does with it is up to you: open the recording in a browser, arrange windows into the stop's layout, anything.

`:view N` asks the same command for one view, with the same environment plus two variables. The command opened the stop's views, so it is the one that can bring back the window already showing a view instead of opening a second:

| Variable | Value |
|----------|-------|
| `MONOCLE_VIEW_INDEX` | Which view, 1-based: its position in the stop's `views` |
| `MONOCLE_VIEW_NAME` | The view's name: `view` for the first, then `view2`, `view3`… |

When these are set, show that one view — open it, or raise it if it is already open — and leave the rest of the screen as it is: the reviewer asked for a view, not for the stop again. Without an on-stop command, `:view N` opens the view in your `media_viewer` (or `markdown_viewer`).

## Asking about a stop

Stop ids are what you type and what the agent answers to. When you ask about one, the agent can call `goto_stop` to put that stop in front of you while it explains.

To ask about particular lines, point at them and send them: select with `v` or a mouse drag, or tag lines one at a time with `+` (yellow in the gutter; they stay tagged across files and stops), then press `@`. monocle hands the tour, the stop and the file lines — the selection and the tags, else the cursor's line — to your [`walkthrough_ask`](/configuration/config-file) command, which puts them in the agent's prompt and moves you there to type the question. The status bar says what went: `sent 2.2 orders.ts:120-124 to the agent`.

`ctrl+]` works out the same lines and asks your [`walkthrough_resolve`](/configuration/config-file) command what they reference — the SQL file a query is loaded from, say — then opens the answer in [the editor beside monocle](#the-editor-beside-monocle), beside what it already holds (at most 8 files) and moves you there: `opened 2: find_by_email.sql, …`, or `nothing to open on these lines`. `p` (or `f16`) previews the first file instead, through [`related_editor_preview`](/configuration/config-file): a passing popup in the editor beside monocle that adds nothing to the pane.

A comment you write while the tour is on is tagged with the stop you were on: it shows `[1.2]` in its box, and the feedback the agent receives leads with it — `[1.2] Does x get hoisted here?` — so the agent reads it against what it said at that stop. If the agent re-sends the tour — to fix a note, say — you stay on the stop you were on as long as its id survives.

## Not covered

A driver can end the tour with a **Not covered** stop: the PR's changed lines that no stop covers, as `hunks`. Its note says how much of the change the tour covers. On it the file list comes up holding only the uncovered files, as wide as their paths need; `.` and `,` step through the uncovered changes one at a time, each marked in the gutter as a stop's lines are, and `>` and `<` jump a file at a time. The note's header names the change on screen and the status bar counts them (`tour uncovered · 9 of 9 · hunk 2 of 7`). Past the last change `.` goes on through the tour, and `,` before the first goes back to the stop before; stepping back into the stop lands on its last change. Leaving it puts the file list back as it was.

## Generated files

A lockfile, a typed client or a swagger spec can be most of a change's lines and none of its decisions. monocle marks such a file generated — by `.gitattributes`' `linguist-generated`, a lockfile's name, a `.gen.` or `.generated.` name, a swagger file, or a marker in its first 5 lines — and the file list badges it `⚙`, after the files someone wrote. Its diff opens folded to a card saying what it is: the tour's line for it (a tour's `generated` notes), the generator its header names, a lockfile's packages added, removed and bumped, a new file's first lines, and its line counts. `Z` shows the diff, and folds it back; a stop at lines of the file shows those lines. A generated file still counts as unreviewed until you mark it with `r`: the card is there to make that quick.

What marks a file generated never comes from the change under review, or the change could fold its own files away: `.gitattributes` is read at the base, and a header marker counts on a file the base has only when the base's version has it too. A file the change adds counts by its own name or header, and its card says the change classified it ("classified by this PR's own name"). A tour's note never makes a file generated. The card strips escape sequences and control bytes from everything it shows.

## Sending a tour

Agents send tours with the `set_walkthrough` MCP tool or `monocle review set-walkthrough --file tour.json`. See [Agent commands](/reference/agent-commands#monocle-review-set-walkthrough) for the format.
