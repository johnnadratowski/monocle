| `g` / `G` | Jump to top/bottom |
| `h` / `l` | Scroll diff left/right |
| `j` / `k` | Move up/down (arrow keys too) |
| `J` / `K` | Scroll diff up/down (any pane) |
| `L` | Scroll diff right (any pane) |
| `0` | Scroll to column 0 (any pane) |
| `$` | Scroll to line end (any pane) |
| `^` | Scroll to first non-space (any pane) |
| `ctrl+d` / `ctrl+u` | Scroll diff half page (any pane) |

## Jump

| Key | Action |
|-----|--------|
| `n` / `N` | Next/previous search match |
| `%` | Between the current block's start and end (vim %) |
| `(` | Out one level, to the enclosing block's opening line (vim [{) |
| `)` | Out to the outermost enclosing block (vim 99[{) |
| `/` / `?` | Search the diff forward/backward (diff focused) |
| `<` / `>` | Previous/next comment or annotation |
| `[` / `]` | Previous/next diff chunk in the diff pane, else previous/next file |
| `{` / `}` | Previous/next file (any pane) |
| `ctrl+i` | Forward again (vim ctrl+i) |
| `ctrl+o` | Back to where you jumped from (vim ctrl+o) |

`%`, `(` and `)` navigate code structure. From inside a nested `if`, `(` goes out to the `if`, and `(` again — or `)` in one press — goes out to the enclosing `func`. `%` toggles between a block's opening line and its closing one.

<Note>
  Vim has no reliable motion to the top of the enclosing function. `[[` looks like one, but `:h [[` defines it as the previous `{` **in the first column** — K&R C layout. In Go, JavaScript, Rust or Python it finds nothing and lands at the top of the file instead. The bracket-aware `[{` is the one that works, and a count climbs several levels: `99[{`. To get the same two motions in vim, add `nnoremap ( [{` and `nnoremap ) 99[{`.
</Note>

Structure is read from brackets where a language has them and from indentation otherwise, so Python, YAML and markdown artifacts work too. Only the lines the pane has actually rendered are searched — in a compact diff a target inside a skipped region isn't found and the motion does nothing, so press `a` for the whole file when you want to navigate past the hunks.

## View & panes

| Key | Action |
|-----|--------|
| `a` | Toggle full-file diff (whole file vs. changed lines) |
| `f` | Cycle sidebar view (flat/tree/grouped) |
| `t` | Cycle diff style (unified/split/file) (any pane) |
| `w` | Toggle line wrapping (any pane) |
| `z` / `e` | Collapse/expand all (tree view) |
| `F` | Toggle focus mode (hide sidebar, wrap lines) |
| `O` | Hide/show inline comments + annotations |
| `T` | Cycle layout (auto/side-by-side/stacked) |
| `1` / `2` | Jump straight to a pane |
| `#` | Cycle source-code comments: dim → hide → show |
| `/` | Sidebar: cycle the reviewed filter |
| `;` | Show/hide the sidebar |
| `enter` | Focus the diff pane / toggle a directory open |
| `tab` / `shift+tab` | Switch pane focus (sidebar/diff/doc) |

The diff pane's borders carry two kinds of fact, split by side.

**Left — what you are looking at.** The file path or artifact title, then how long ago it last changed (an artifact's send time, a file's mtime) as `now` / `5m` / `3h` / `2d` / `3w`, then its change kind — `added`, `modified`, `deleted`, `renamed` — coloured to match the sidebar's `A`/`M`/`D`/`R` letter. Artifacts and added context files show no change kind, since neither is part of the diff.

**Right — what state it is in.** The view-mode badge and how much content runs off that edge: `↑ 128 lines · 3 chunks` in the top border, `↓ 940 lines · 12 chunks` in the bottom. A "chunk" is the same unit `[` and `]` jump between, so the count tells you how many more presses there are that way. A missing marker means that end is already on screen.

The badge names each dimension that is not at its default: how much of the file is shown (hunks, or `ALL` of it) and how it is laid out (`UNIFIED` or `SPLIT`). The layout is spelled out whenever `ALL` is, because `ALL` on its own reads as though it replaced the layout — `[ALL · UNIFIED]`, `[ALL · SPLIT]`. A plain `[SPLIT]` needs no such qualifier, and the all-defaults view carries no badge at all, so a badge appearing always means you are not in the default view.

```
┌─ internal/core/engine_impl.go · 12m · modified ────── [ALL] ↑ 128 lines · 3 chunks ─┐
│                                                                                     │
└─────────────────────────────────────────────────────────── ↓ 940 lines · 12 chunks ─┘
```

On a narrow pane, chips shed from most re-derivable elsewhere to least: the age first, then the status (the sidebar shows it too), then the scroll marker — shortening to `↑128 ·3` before disappearing — then the mode badge, which nothing else in the UI reports. The file name is surrendered last, and when it has to be shortened it keeps both ends — `internal/…engine_impl.go`, `pseudocode: … in the swap path` — rather than only the tail, since an artifact's subject is at the front. The cut snaps to a path separator where one is near, so a filename stays whole.

The line under the cursor always wraps when it runs off the right edge, even with wrap mode off, so you never have to scroll sideways to read the line you are on. Only that line expands — the rest of the diff keeps its one-row-per-line shape. Wrapped rows keep their colouring in full — syntax highlighting, the line background, and the brighter span marking the words that actually changed. The whole line is coloured first and the styled result is then split, so a wrapped line looks identical to the same line unwrapped. `w` wraps in split view too. Each half wraps on its own and the halves are zipped back row by row, so the divider stays in one column and a long line on one side never drags the other out of alignment. Wrapping turns off horizontal scrolling and intra-line change highlighting for the wrapped row — the line-level added/removed background still shows which side changed.

`ctrl+h` / `ctrl+j` / `ctrl+k` / `ctrl+l` move focus between monocle's panes, following [vim-tmux-navigator](https://github.com/christoomey/vim-tmux-navigator): when there is no pane that way, the key is handed to tmux as `select-pane` so focus leaves monocle instead of stopping. The key is never dropped — a direction monocle cannot act on always reaches tmux, since silently swallowing it makes navigation appear broken one way with no feedback. Active only inside tmux; elsewhere the keys keep whatever they meant before.

Inside the comment or submit editor they keep their editing meaning — `ctrl+k` still kills to end of line — the same way these keys stay out of vim's insert mode. `ctrl+\` is deliberately not bound: tmux owns last-pane.

When a new review arrives — the agent's first batch of work after your feedback reached it — the sidebar scrolls back to the top and selects the first item, rather than leaving the cursor wherever the previous round ended. It fires once per review, so the agent editing files mid-review never moves your cursor.

When the agent sends groupings (`set_file_groups`), the sidebar switches to grouped view on its own the first time they arrive, so the reading order the agent chose is visible without hunting for it. It happens once per session — after that `f` is yours and a refresh won't drag you back.

## Review verdicts

When you submit (`S`), `Tab` cycles the verdict. All three are delivered the same way; they differ in what they tell the agent and in what happens to the review.

| Verdict | Tells the agent | Review state |
|---------|-----------------|--------------|
| `APPROVE` | Done — ship it | Closed. Artifacts, added files and the review name are cleared, and the base ref returns to `HEAD` |
| `QUESTIONS` | Answer these before continuing; change code only where an answer turns out to require it | Stays open, exactly as for changes requested |
| `REQUEST CHANGES` | Address the comments and resubmit | Stays open; a snapshot is taken so the next round diffs against it |

Individual comments carry a type too — `Q` asks a question at the cursor and `A` answers one, or `Tab` in the comment editor cycles issue → suggestion → question → answer → note → praise. An **answer** replies to something the agent raised and asks nothing back, so a review of nothing but answers defaults to `APPROVE`: you have told the agent what it needed and you are done. Leave only questions and the submit modal defaults to the `QUESTIONS` verdict; add an issue or a suggestion and it defaults to `REQUEST CHANGES`, because the agent has to change code either way.

`QUESTIONS` exists for the case where a comment is genuinely a question. Approving closes the review and reads as "ship it"; requesting changes tells the agent to edit code it may not need to touch. Both verdicts that keep the review open require at least one comment or some body text — blocking the agent with nothing to act on is never what you want.
